其中最需要注意的是文法中的左递归，例如：


```cpp
#ifndef SYNTAX_NODE_H
#define SYNTAX_NODE_H

#include <optional>
#include <vector>

#include "common/Token.h"
#include "parser/SyntaxType.h"

struct SyntaxNode
{
    // 终结符节点使用 token
    std::optional<Token> token;

    // 非终结符节点使用 syntaxType
    std::optional<SyntaxType> syntaxType;

    // 按源代码顺序保存子节点
    std::vector<SyntaxNode> children;

    // 创建终结符节点
    explicit SyntaxNode(const Token &value)
        : token(value)
    {
    }

    // 创建非终结符节点
    explicit SyntaxNode(SyntaxType value)
        : syntaxType(value)
    {
    }
};

#endif
```

使用方式：

```cpp
Token token(TokenType::INTTK, "int", 1);

// 终结符节点
SyntaxNode tokenNode(token);

// 非终结符节点

// 把终结符加入非终结符
mainNode.children.push_back(tokenNode);
```

“统一叫 `node`”这个想法是对的，但一个结构体里不能声明两个同名成员：

```cpp
optional<Token> node;
optional<SyntaxType> node; // 重名，编译器无法区分
```

这种“一个变量可能是两种类型之一”的情况，更适合使用 `std::variant`：

```cpp
#ifndef SYNTAX_NODE_H
#define SYNTAX_NODE_H

#include <variant>
#include <vector>

#include "common/Token.h"
#include "parser/SyntaxType.h"

struct SyntaxNode
{
    std::variant<Token, SyntaxType> node;
    std::vector<SyntaxNode> children;

    explicit SyntaxNode(const Token &value)
        : node(value)
    {
    }

    explicit SyntaxNode(SyntaxType value)
        : node(value)
    {
    }
};

#endif
```

`variant<Token, SyntaxType>` 表示：`node` 中只能保存 `Token` 或 `SyntaxType` 中的一种。

判断节点类型：

```cpp
if (std::holds_alternative<Token>(syntaxNode.node))
{
    // 这是终结符节点
}
else
{
    // 这是非终结符节点
}
```

取出其中的数据：

```cpp
Token token = std::get<Token>(syntaxNode.node);

SyntaxType type = std::get<SyntaxType>(syntaxNode.node);
```

这比两个 `optional` 更严谨，因为两个 `optional` 可能同时为空或同时有值；`variant` 能保证任何时候恰好保存一种类型。

另外，`SyntaxType` 是枚举，体积很小，构造函数直接按值传递即可：

```cpp
SyntaxNode(SyntaxType value)
```

不需要写成 `const SyntaxType &value`。

`Parser.h` 先规划成这样：

```cpp
#ifndef PARSER_H
#define PARSER_H

#include <cstddef>
#include <vector>

#include "common/Token.h"
#include "parser/SyntaxNode.h"

class Parser
{
private:
    const std::vector<Token> &tokens;
    std::size_t pos = 0;

    bool atEnd() const;
    const Token &current() const;
    const Token &lookAhead(std::size_t offset) const;
    bool check(TokenType type) const;
    Token consume(TokenType expected);

    SyntaxNode parseCompUnit();
    SyntaxNode parseMainFuncDef();
    SyntaxNode parseBlock();

public:
    explicit Parser(const std::vector<Token> &tokens);

    SyntaxNode parse();
};

#endif
```

这几个工具函数分别负责：

- `atEnd()`：判断 `pos >= tokens.size()`。
- `current()`：返回 `tokens[pos]`，不移动位置。
- `lookAhead(offset)`：查看后面的 Token，仍然不移动位置。
- `check(type)`：判断当前 Token 的类型。
- `consume(expected)`：检查当前 Token，保存它，然后让 `pos++`。
- `parse()`：语法分析的统一入口，内部调用 `parseCompUnit()`。

例如分析：

```c
int main() {}
```

Token 流是：

```text
INTTK MAINTK LPARENT RPARENT LBRACE RBRACE
  ↑
 pos
```

每调用一次 `consume()`，`pos` 就向右移动一次。

目前先只处理正确程序。如果 `consume()` 发现类型不符合，可以临时抛出异常，方便发现自己的分析逻辑错误：

```cpp
Token Parser::consume(TokenType expected)
{
    if (atEnd() || !check(expected))
    {
        throw std::runtime_error("unexpected token");
    }

    return tokens[pos++];
}
```

之后开始处理 `i/j/k` 类错误时，再把这里细分成错误记录和恢复逻辑。

可以把语法分析理解成：把一串零散的 Token，组合成有层次的程序结构。

例如源代码：

```c
int main() {
}
```

经过词法分析后得到：

```text
INTTK int
MAINTK main
LPARENT (
RPARENT )
LBRACE {
RBRACE }
```

这些 Token 再由语法分析组合为：

```text
CompUnit
└── MainFuncDef
    ├── INTTK int
    ├── MAINTK main
    ├── LPARENT (
    ├── RPARENT )
    └── Block
        ├── LBRACE {
        └── RBRACE }
```

### 终结符

终结符是语法树最底层、不能继续拆分的符号。在你的编译器中，词法分析产生的每个 `Token` 都是终结符。

例如：

```text
INTTK int
MAINTK main
LPARENT (
INTCON 123
PLUS +
IDENFR number
```

一个 Token 包含：

```cpp
struct Token
{
    TokenType type; // 类别，例如 INTTK
    string s;       // 原始内容，例如 int
    int line;       // 所在行
};
```

之所以叫“终结符”，是因为语法分析到这里就结束了，不会再用其他文法规则展开它。

在你的 `SyntaxNode` 中，保存 `Token` 的节点就是终结符节点：

```cpp
SyntaxNode(consume(TokenType::INTTK))
```

### 非终结符

非终结符是由一个或多个终结符、其他非终结符组合成的结构。

例如课程文法中：

```text
MainFuncDef → 'int' 'main' '(' ')' Block
```

左边的 `MainFuncDef` 是非终结符，右边包含：

```text
'int'    终结符
'main'   终结符
'('      终结符
')'      终结符
Block    非终结符
```

`Block` 又可以继续展开：

```text
Block → '{' { BlockItem } '}'
```

所以它也是非终结符。

在你的程序中，`SyntaxType` 中的成员全都是非终结符：

```cpp
SyntaxType::CompUnit
SyntaxType::MainFuncDef
SyntaxType::Block
SyntaxType::Stmt
SyntaxType::AddExp
```

例如：

```cpp
SyntaxNode node(SyntaxType::MainFuncDef);
```

创建的就是非终结符节点。

### 语法成分

“语法成分”是对程序结构的中文称呼。在这份实验要求中，它基本上就是非终结符所表示的结构。

例如：

| 源代码 | 识别出的语法成分 |
|---|---|
| `123` | `<Number>` |
| `a` | `<LVal>` |
| `1 + 2` | `<AddExp>` |
| `return 0;` | `<Stmt>` |
| `{ return 0; }` | `<Block>` |
| `int main() {}` | `<MainFuncDef>` |
| 整个源程序 | `<CompUnit>` |

例如：

```c
return 1 + 2;
```

其中可以识别出很多层语法成分：

```text
Stmt
```

最核心的区别是：

- `PrimaryExp`：最基础、不可再按运算符拆分的表达式。
- `UnaryExp`：在基础表达式外面加单目运算、函数调用或类型转换形成的表达式层。

课程文法是：

```text
PrimaryExp → '(' Exp ')' | LVal | Number
```

所以 `PrimaryExp` 包括：

```c
123          // Number
'a'          // Number
x            // LVal
array[2]     // LVal
(a + 1)      // 括号表达式
```

而 `UnaryExp` 是：

```text
UnaryExp → PrimaryExp
         | Ident '(' [FuncRParams] ')'
         | UnaryOp UnaryExp
         | '(' BType ')' UnaryExp
```

因此它包括：

```c
123          // PrimaryExp
x            // PrimaryExp
(a + 1)      // PrimaryExp

-123         // UnaryOp UnaryExp
!x           // UnaryOp UnaryExp
f(1, 2)      // 函数调用
(int)x       // 类型转换
```

可以理解为下面的包含关系：

```text
UnaryExp
├── 普通基础表达式 PrimaryExp
├── 单目运算
├── 函数调用
└── 类型转换
```

例如普通变量 `a`：

```text
UnaryExp
└── PrimaryExp
    └── LVal
        └── IDENFR a
```

而 `-a`：

```text
UnaryExp
├── UnaryOp
│   └── MINU -
└── UnaryExp
    └── PrimaryExp
        └── LVal
            └── IDENFR a
```

注意 `UnaryOp UnaryExp` 的右边仍然是 `UnaryExp`，所以可以支持连续单目运算：

```c
--a
!!a
-!a
```

例如 `--a`：

```text
UnaryExp
├── UnaryOp：-
└── UnaryExp
    ├── UnaryOp：-
    └── UnaryExp
        └── PrimaryExp：a
```

函数调用直接属于 `UnaryExp`：

```c

```

对应：

```text
UnaryExp
├── IDENFR f
├── LPARENT (
├── FuncRParams
└── RPARENT )
```

函数调用虽然不是传统意义上的“单目运算”，但课程文法把它放在 `UnaryExp` 这一优先级层，因此代码必须照文法处理。


```text

```

```cpp
    while (check(TokenType::MULT) ||
           check(TokenType::DIV) ||
           check(TokenType::MOD))

        // 用新的 MulExp 包住前面的结果

        parent.children.push_back(std::move(left));
        parent.children.emplace_back(consume(operatorType));
        parent.children.push_back(parseUnaryExp());

        left = std::move(parent);
    }

    return left;
}
```

左递归指的是：一个语法成分的规则右边，最左边又出现了它自己。

例如：

```text
MulExp → MulExp ('*' | '/' | '%') UnaryExp
```

右边第一个符号又是 `MulExp`：

```text
MulExp → MulExp ...
         ↑
       自己
```

所以叫“左递归”。

它描述的是：一个乘除表达式，可以由“前面已经形成的乘除表达式”，再接一个运算符和新的 `UnaryExp` 组成。

例如：

```c
2 * 3 / 4
```

形成过程是：

```text
2
↓ 接上 * 3
2 * 3
↓ 接上 / 4
(2 * 3) / 4
```

用文法表示就是：

```text
MulExp
→ MulExp / UnaryExp
→ MulExp * UnaryExp / UnaryExp
→ UnaryExp * UnaryExp / UnaryExp
```

“递归”是因为 `MulExp` 的定义中再次使用了 `MulExp`；“左”是因为它出现在规则右边的最左侧。

### 为什么不能直接照文法写代码

如果直接翻译成递归函数，可能写成：

```cpp
SyntaxNode Parser::parseMulExp()
{
    parseMulExp();
    // 读取运算符
    parseUnaryExp();
}
```

调用过程会变成：

```text
parseMulExp()
  → parseMulExp()
      → parseMulExp()
          → parseMulExp()
              → ...
```

此时一个 Token 都还没读取，函数就不断调用自己，最终栈溢出。

因此，递归下降分析器需要把左递归改成循环。

原文法：

```text
MulExp → UnaryExp
       | MulExp ('*' | '/' | '%') UnaryExp
```

代码使用的等价思路：

```text
MulExp → UnaryExp
         { ('*' | '/' | '%') UnaryExp }
```

其中 `{ ... }` 表示可以重复零次或多次。

对应代码结构：

```cpp
先分析一个 UnaryExp

while（当前是 *、/、%）
{
    读取运算符;
    再分析一个 UnaryExp;
}
```

例如 `2 * 3 / 4`：

```text
先读取 2

看到 *
读取 * 和 3

看到 /
读取 / 和 4

后面不再是乘除模
结束
```

### 左递归还表达了左结合

文法：

```text
MulExp → MulExp '*' UnaryExp
```

左侧是之前形成的 `MulExp`，所以：

```c
8 / 4 / 2
```

会理解成：

```c
(8 / 4) / 2
```

而不是：

```c
8 / (4 / 2)
```

所以可以这样记：

> 左递归就是“先把左边算成一个结果，再不断把后面的运算接上去”。

你的语法中这些都是左递归：

```text
MulExp  → MulExp  ('*' | '/' | '%') UnaryExp
AddExp  → AddExp  ('+' | '-') MulExp
RelExp  → RelExp  ('<' | '>' | '<=' | '>=') AddExp
EqExp   → EqExp   ('==' | '!=') RelExp
LAndExp → LAndExp '&&' EqExp
LOrExp  → LOrExp  '||' LAndExp
```

它们都使用同一种处理方法：代码中用循环读取，建树时每遇到一个运算符就用新的父节点包住左边已有的结果。

这里是 `std::move`，它表示：把一个对象已有的数据转交给另一个对象，尽量避免复制。

代码：

```cpp
parent.children.push_back(std::move(left));
```

意思是：

> 把 `left` 中的整棵语法树转交给 `parent.children`。

假设 `left` 当前保存：

```text
MulExp
├── MulExp：2
├── MULT *
└── UnaryExp：3
```

现在读到了 `/ 4`，需要创建新的父节点：

```text
parent
├── 原来的 left
├── DIV /
└── UnaryExp：4
```

于是：

```cpp
parent.children.push_back(std::move(left));
```

把原来的树放进 `parent.children`。

如果不写 `move`：

```cpp
parent.children.push_back(left);
```

会复制一整棵树：

```text
left                    parent.children[0]
原始语法树    复制 →     新语法树副本
```

语法树越大，复制的节点越多。

使用 `std::move`：

```cpp
parent.children.push_back(std::move(left));
```

会尽量直接转移内部数据：

```text
left  ─────转交─────>  parent.children[0]
```

你的 `SyntaxNode` 里面有：

```cpp
vector<SyntaxNode> children;
```

`vector` 内部管理一块动态内存。移动时通常只需要转交这块内存的所有权，不需要把里面所有节点逐个复制。

需要注意：`std::move` 之后，原来的 `left` 仍然存在，但它内部的内容已经被转移，不能继续依赖其原值。

所以紧接着会重新给它赋值：

```cpp
left = std::move(parent);
```

完整过程是：

```cpp
// 把旧 left 放入新 parent
parent.children.push_back(std::move(left));

// 新 parent 变成新的 left
left = std::move(parent);
```

可以把它想象成搬家：

```text
push_back(left)             复制一套家具
push_back(std::move(left))  把原来的家具直接搬过去
```

严格来说，`std::move` 自己并没有移动数据，它只是告诉编译器：

> 这个对象原来的内容以后不再需要，可以调用移动构造或移动赋值。

它定义在：

```cpp
#include <utility>
```

你目前使用了：

```cpp
#include <bits/stdc++.h>
```

其中已经间接包含了 `<utility>`。

在当前程序中不写 `std::move` 通常也能得到正确结果：

```cpp
parent.children.push_back(left);
```

只是会复制语法树。使用 `std::move(left)` 更符合“旧的 `left` 已经要成为新父节点的子节点”这个含义，也更高效。

`parseStmt()` 的意思是：

```text
parse + Stmt
分析      语句
```

其中 `Stmt` 是 `Statement`（语句）的缩写。

它负责从当前 `pos` 开始，识别一整条语句，并返回一个 `SyntaxType::Stmt` 节点。

例如下面每一项都是一条 `Stmt`：

```c
a = 1;                 // 赋值语句
1 + 2;                 // 表达式语句
;                      // 空语句
return 0;              // 返回语句
break;                 // break 语句
continue;              // continue 语句
if (a) return 1;       // if 语句
while (a) {}           // while 语句
{ int a; }             // 语句块
printf("hello\n");     // 输出语句
```

课程文法中：

```text
Block → '{' { BlockItem } '}'

BlockItem → Decl | Stmt
```

所以遇到：

```c
int main() {
    int a;       // Decl
    a = 1;       // Stmt
    return a;    // Stmt
}
```

调用关系大致是：

```text
parseBlock()
├── parseBlockItem()
│   └── parseDecl()       // int a;
├── parseBlockItem()
│   └── parseStmt()       // a = 1;
└── parseBlockItem()
    └── parseStmt()       // return a;
```

`parseStmt()` 会查看当前 Token，判断是哪种语句：

```text
当前是 RETURNTK    → return 语句
当前是 IFTK        → if 语句
当前是 WHILETK     → while 语句
当前是 BREAKTK     → break 语句
当前是 CONTINUETK  → continue 语句
当前是 LBRACE      → 语句块
当前是 SWITCHTK    → switch 语句
当前是 PRINTFTK    → printf 语句
其他               → 赋值、表达式或空语句
```

例如当前 Token 是：

```text
RETURNTK return
INTCON 1
PLUS +
INTCON 2
SEMICN ;
```

`parseStmt()` 会建立：

```text
Stmt
├── RETURNTK return
├── Exp
│   └── AddExp
│       ├── 1
│       ├── PLUS +
│       └── 2
└── SEMICN ;
```

第一阶段只需要让它支持：

```text
Stmt → 'return' [Exp] ';'
```

逻辑是：

```text
创建 Stmt 节点
读取 return
如果后面不是分号
    调用 parseExp()
读取分号
返回 Stmt 节点
```

所以 `parseStmt()` 本身不负责分析表达式的内部结构。它看到 `return` 后，把表达式部分交给：

```cpp
parseExp();
```

可以把它理解为一个“语句总入口”：先判断语句种类，再把其中更小的结构交给对应的分析函数。

这是**深度优先的后序遍历**，并且兄弟节点按照从左到右的顺序遍历。

你的输出函数逻辑是：

```cpp
for (const SyntaxNode &child : node.children)
{
    printSyntaxTree(child, output);
}

// 所有子节点输出完，最后输出自己
output << "<" << SyntaxTypeToString(type) << ">\n";
```

因此规则是：

```text
先遍历所有子节点
最后输出当前非终结符节点
```

终结符 `Token` 是叶子节点，没有子节点，所以遇到后立即输出。

例如：

```c
return 1;
```

语法树大致是：

```text
Stmt
├── RETURNTK return
├── Exp
│   └── AddExp
│       └── MulExp
│           └── UnaryExp
│               └── PrimaryExp
│                   └── Number
│                       └── INTCON 1
└── SEMICN ;
```

后序遍历首先一路向下：

```text
Stmt
→ Exp
→ AddExp
→ MulExp
→ UnaryExp
→ PrimaryExp
→ Number
→ INTCON 1
```

到达叶子后开始输出并逐层返回：

```text
INTCON 1
<Number>
<PrimaryExp>
<UnaryExp>
<MulExp>
<AddExp>
<Exp>
```

回到 `Stmt` 后继续遍历分号：

```text
SEMICN ;
```

最后才输出当前节点：

```text
<Stmt>
```

因此完整顺序是：

```text
RETURNTK return
INTCON 1
<Number>
<PrimaryExp>
<UnaryExp>
<MulExp>
<AddExp>
<Exp>
SEMICN ;
<Stmt>
```

对于：

```c
1 + 2 * 3
```

最外层 `AddExp` 可以简化为：

```text
AddExp
├── AddExp：1
├── PLUS +
└── MulExp：2 * 3
```

后序遍历顺序是：

```text
1. 遍历左边 AddExp：1
2. 输出 PLUS +
3. 遍历右边 MulExp：2 * 3
4. 输出最外层 <AddExp>
```

所以会看到：

```text
INTCON 1
...
<AddExp>       ← 左边的 AddExp
PLUS +
INTCON 2
...
MULT *
INTCON 3
...
<MulExp>
<AddExp>       ← 最外层的 AddExp
```

第一个 `<AddExp>` 出现在 `PLUS` 前面，是因为它属于左子树；最后一个 `<AddExp>` 才是整个 `1 + 2 * 3`。

可以这样记：

> Token 按源代码顺序输出；某个语法成分的所有内容输出完成后，再输出 `<语法成分>`。

这正是课程评测要求的输出方式。对于这种多叉语法树，通常称为“从左到右的深度优先后序遍历”。
